Application code can be flawless and still be breached through its **surroundings**: an API key committed to GitHub, an overly powerful IAM role, a public storage bucket, a compromised dependency or CI pipeline, or an attack nobody noticed for months. **Infrastructure security** covers secrets management, identity and access in the cloud, network isolation, the software supply chain, and the ability to **detect and respond** to incidents.

<Analogy>
  A bank's vault door can be excellent, but if the combination is written on a sticky note in the lobby (leaked secret), the cleaning crew has a master key to every room (over-privileged role), or nobody watches the security cameras (no monitoring), the door doesn't matter.
</Analogy>

## Why it matters

Leaked credentials and misconfigured cloud resources cause a large share of real breaches. Senior interviews expect answers about secret storage and rotation, IAM least privilege, network design and incident handling.

## Secrets management

A **secret** is anything that grants access: database passwords, API keys, signing keys, OAuth client secrets, TLS private keys.

If a secret leaks: **revoke and rotate immediately** (deleting the commit isn't enough — history, forks and caches keep it), then investigate its use.

## Cloud identity and least privilege

- Use **roles**, not long-lived access keys: EC2/ECS/Lambda roles, Kubernetes service accounts mapped to cloud roles (IRSA, Workload Identity), CI with **OIDC federation** instead of stored cloud keys.
- **Least privilege**: grant specific actions on specific resources (`s3:GetObject` on one bucket), not `*:*`. Start narrow; use access analysers to trim unused permissions.
- **Separate accounts/projects** for production, staging and development; tightly control who can access production.
- **MFA** and short sessions for humans; break-glass procedures for emergencies.
- Guardrails: organisation policies that forbid public buckets, unencrypted storage, or regions you don't use.

## Network security

- Public entry only through the load balancer/CDN with a WAF; everything else in **private subnets**.
- **Security groups / network policies** allow only required flows (app → DB on 5432, nothing else).
- Restrict **egress** too — it limits data exfiltration and SSRF damage.
- Encrypt internal traffic (TLS/mTLS) — zero trust rather than relying on the perimeter.
- Admin access via SSO-backed session managers or bastions, never open SSH to the internet.

## Software supply chain

Your build pipeline is a production system with the keys to everything.

| Risk | Control |
|---|---|
| Vulnerable or malicious dependencies | lockfiles, `npm ci`, dependency scanning, careful additions, pinned versions |
| Compromised CI | least-privilege CI roles, OIDC to cloud, protected branches, required reviews |
| Tampered artefacts | build once, sign images (Sigstore/cosign), verify signatures at deploy |
| Unknown contents | SBOMs (software bill of materials) per build |
| Vulnerable base images | minimal/distroless images, regular rebuilds, image scanning |

Frameworks like **SLSA** describe maturity levels for build integrity.

## Data protection

Classify data (public, internal, confidential, regulated); encrypt at rest and in transit; minimise what you collect and keep (retention policies); mask or tokenise sensitive fields; restrict who can query production data; and know your regulatory duties (GDPR, PCI DSS for cards, HIPAA for health data).

## Detection and incident response

Assume something will eventually go wrong; the difference is how fast you notice and respond.

- **Log** security-relevant events centrally and immutably: logins, permission changes, admin actions, access-denied spikes, cloud API calls (CloudTrail).
- **Alert** on anomalies: unusual geographies, impossible travel, sudden data exports, disabled logging, new IAM users.
- **Incident response plan**:

Also: preserve evidence, communicate clearly (internally, to customers, and to regulators within legal deadlines), and practise with tabletop exercises.

<Callout type="pitfall" title="Common mistakes">

- Secrets in git, environment files in images, or printed in logs.
- Long-lived cloud access keys for CI or humans.
- `AdministratorAccess` for application roles.
- Public buckets or databases "temporarily".
- No egress restrictions; flat networks.
- No audit logs, or logs nobody reviews.

</Callout>

## Explaining it in an interview

<InterviewAnswer question="How do you manage secrets and access for services in the cloud?">

Secrets live only in a managed store such as AWS Secrets Manager or Vault, encrypted with KMS keys and access-logged — never in git, images or logs, with secret scanning in CI to catch mistakes. Workloads authenticate with their own identities — IAM roles, or Kubernetes service accounts mapped to cloud roles — so there are no bootstrap passwords, and CI uses OIDC federation instead of stored keys. Each role has least-privilege permissions on specific resources, and secrets are rotated automatically, ideally as short-lived dynamic database credentials. Networking keeps services and databases in private subnets behind a WAF and load balancer, with tight security groups and restricted egress. Builds are reproducible from lockfiles, images are scanned and signed, and CloudTrail plus application security logs feed alerts and a practised incident response plan. If a secret leaks, I revoke and rotate it first, then investigate.

<Fragment slot="deeper">

- **Why not just delete a leaked key from git?** History, forks and caches keep it — rotate immediately.
- **What is workload identity?** Giving each workload its own cloud identity instead of shared static credentials.
- **What is an SBOM?** A list of all components in a build, used to track vulnerabilities.

</Fragment>
</InterviewAnswer>
