Some operating-system operations have no truly asynchronous version — reading a file, looking up a hostname with `getaddrinfo`, hashing a password. If Node ran them on the main thread, everything would stop. So libuv keeps a small **thread pool** — **4 threads by default** — and hands those jobs to it. A pool thread does the blocking work, and when it finishes, the completion callback is queued for the main JavaScript thread to run in the poll phase.

<Analogy>
  A restaurant's waiter (the JS thread) never cooks. Orders that need slow, hands-on work go to the kitchen, which has four cooks (the pool). If ten complicated orders arrive at once, four are cooked and six wait for a free cook — and a simple side salad ordered after them waits too, even though it would only take a minute.
</Analogy>

## Why it matters

Pool saturation is a classic hidden latency source: a burst of password hashing or large file reads slows down unrelated endpoints, while CPU looks fine and nothing appears "blocked". Interviewers ask which operations use the pool, its default size, and why networking doesn't.

| Uses the thread pool | Does **not** use it |
|---|---|
| `fs.readFile`, `fs.writeFile`, `fs.promises.*` (all async fs) | TCP/HTTP sockets, `net`, `http`, `https` data transfer |
| `dns.lookup` (and thus `http.get('http://hostname')`) | `dns.resolve*` (uses c-ares, truly async) |
| `crypto.pbkdf2`, `scrypt`, `randomBytes` (async), key generation | `crypto.createHash().update()` (synchronous, on the main thread!) |
| `zlib.gzip` and other async compression | Timers |

Networking does not need threads because the OS can watch thousands of sockets at once and report which ones are ready. That is how one Node process holds tens of thousands of connections.

## Saturation

With four threads, the fifth concurrent pool job **waits**.

```js
const crypto = require('node:crypto');
const start = Date.now();

for (let i = 1; i <= 6; i++) {
  crypto.pbkdf2('secret', 'salt', 300_000, 64, 'sha512', () => {
    console.log(`job ${i} done after ${Date.now() - start} ms`);
  });
}
// four jobs finish around T ms; jobs 5 and 6 around 2T ms
```

## Sizing the pool

Set the environment variable **before the process starts**:

```bash
UV_THREADPOOL_SIZE=16 node server.js
```

- Maximum is 1024. libuv reads it when the pool is first used, so setting `process.env.UV_THREADPOOL_SIZE` inside your code only works if no pool work has happened yet (and some modules use the pool during startup). Prefer the real environment variable.
- More threads help for **I/O-ish** pool work (many file reads, DNS lookups) up to a point.
- For **CPU-bound** pool work (pbkdf2, scrypt), more threads than CPU cores just adds context switching. Measure; don't guess.

## Practical guidance

- **Password hashing at scale**: use the async API (never `*Sync` in a request) and consider a dedicated worker pool or service so logins don't starve file access.
- **DNS**: if you make many outbound HTTP calls to hostnames, `dns.lookup` can saturate the pool. Use keep-alive agents (fewer lookups), cache DNS, or a resolver based on `dns.resolve`.
- **`fs.promises` is not more parallel** than callback `fs` — both use the same pool.
- **Streams** read files in chunks through the pool; many concurrent large file streams compete for threads.
- **Synchronous crypto hashing** (`createHash`) runs on the main thread; hashing a huge buffer blocks the loop. Stream large inputs.

## How you'd notice saturation

Symptoms: latency rising on endpoints that only read a small file or make an outbound call, while CPU isn't pegged, correlated with traffic on hashing or file-heavy endpoints. Confirm by:

- measuring event-loop delay (if it's low, the main thread isn't the problem),
- tracing how long pool operations wait vs. run,
- testing whether raising `UV_THREADPOOL_SIZE` improves p99 latency.

<Callout type="pitfall" title="Common mistakes">

- Believing HTTP requests use the thread pool. Network sockets don't (but `dns.lookup` for the hostname does).
- Setting `UV_THREADPOOL_SIZE` too late in code.
- Raising the pool size far beyond the core count for CPU-bound work.
- Putting genuinely CPU-heavy computation in the pool instead of worker threads.

</Callout>

## Explaining it in an interview

<InterviewAnswer question="What is the libuv thread pool and what runs on it?">

libuv keeps a pool of four threads by default for operations the OS can only do in a blocking way: file system calls, `dns.lookup`, async crypto like `pbkdf2` and `scrypt`, and zlib compression. The main thread hands the job to the pool and keeps going; the callback runs back on the main thread in the poll phase. Networking doesn't use the pool — sockets are watched by the kernel through epoll or kqueue — which is why Node handles so many connections. The risk is saturation: with four threads busy hashing passwords, unrelated file reads queue behind them. You can raise `UV_THREADPOOL_SIZE` at startup, but for CPU-heavy work worker threads or a separate service are better.

<Fragment slot="deeper">

- **Why is `dns.lookup` on the pool but `dns.resolve` not?** `lookup` uses the OS's blocking `getaddrinfo`; `resolve` uses c-ares, which is asynchronous.
- **Does `fs.promises` avoid the pool?** No.
- **How would you size the pool?** Measure: increase towards core count for CPU-bound pool work, higher for I/O-bound, and watch p99.

</Fragment>
</InterviewAnswer>
