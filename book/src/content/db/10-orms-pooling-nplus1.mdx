A Node service doesn't open a fresh database connection per request — that would be far too slow. It keeps a **connection pool**: a small set of open connections that requests borrow and return. On top of the driver, many teams use an **ORM** (Object-Relational Mapper — Prisma, TypeORM, Sequelize, Drizzle, MikroORM) or a **query builder** (Knex, Kysely) to write queries in TypeScript instead of raw SQL. Both layers are convenient — and both hide performance traps.

<Analogy>
  A connection pool is a taxi rank with a fixed number of cabs. Passengers (requests) take a cab, make their trip (query or transaction), and return it to the rank. If trips take too long or someone keeps a cab parked while they go shopping (an open transaction waiting on an HTTP call), the queue at the rank grows — even though the city's roads (the database) are empty.
</Analogy>

## Why it matters

"The database is slow" is often really "the pool is exhausted" or "the ORM is running 300 queries per request". Interviewers ask about connection pooling, pool sizing, ORM trade-offs and the N+1 problem.

## Why pool connections

Opening a PostgreSQL connection involves a TCP handshake, TLS, authentication and starting a backend **process** on the server (several MB of memory each). That's milliseconds per connection and real server resources. A pool pays that cost once.

```js
const { Pool } = require('pg');

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10,                        // per process!
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 2_000, // fail fast instead of queueing forever
  statement_timeout: 5_000,       // server-side cap on query time
});

// single query: borrow and return automatically
const { rows } = await pool.query('SELECT * FROM users WHERE id = $1', [id]);
```

For transactions, check out one client and **always** release it (see *ACID*).

## Sizing the pool

More connections is not faster. A database server can only run as many queries truly in parallel as it has CPU cores and disk bandwidth; beyond that, connections just contend. A common starting formula for the **total** across all app instances: roughly `cores × 2` (plus a little for disks), then measure.

The trap is **multiplication**:

<Diagram
  caption="Pool size is per process. Replicas × processes × pool size can easily exceed the database's connection limit."
  chart={`flowchart LR
    K["20 pods"] --> X["× 4 cluster workers"] --> Y["× pool max 20"] --> Z["= 1,600 connections"]
    Z --> L["PostgreSQL max_connections = 200 ✗"]`}
/>

Solutions: smaller per-process pools; a **server-side pooler** like **PgBouncer** (or RDS Proxy) in transaction-pooling mode, which multiplexes many client connections onto few database connections; and for serverless functions, always use a proxy, since each function instance opens its own connections.

### Symptoms of pool exhaustion

- Requests time out waiting for a connection while the database CPU is low.
- Latency rises sharply with traffic.
- Usually caused by: transactions held open during slow external calls, leaked clients never released, or a pool much smaller than concurrency.

Monitor `pool.totalCount`, `pool.idleCount` and `pool.waitingCount`.

## ORMs: what they give and what they hide

| Benefits | Risks |
|---|---|
| Type-safe queries and results (Prisma, Drizzle, Kysely) | Hidden queries: lazy loading, N+1 |
| Migrations, schema in code | Inefficient SQL for complex queries |
| Less boilerplate for CRUD | Leaky abstraction: you still need SQL knowledge |
| Parameterisation by default | Over-fetching (all columns, all relations) |

Most teams settle on: ORM or query builder for everyday CRUD, **raw SQL** for complex reporting queries, and **always** look at the SQL the ORM generates (enable query logging in development).

## N+1 through an ORM

The pattern from the previous chapter, as it usually appears:

```ts
// N+1: one query for posts, then one per post when author is accessed
const posts = await prisma.post.findMany({ take: 50 });
for (const post of posts) {
  const author = await prisma.user.findUnique({ where: { id: post.authorId } });
}

// fixed: eager-load the relation
const postsWithAuthors = await prisma.post.findMany({
  take: 50,
  include: { author: { select: { id: true, name: true } } },
});
```

In GraphQL, where resolvers fetch per field, the standard fix is **DataLoader**: it collects all IDs requested in one tick and issues a single batched query.

## Other ORM pitfalls

- **Transactions**: use the ORM's transaction API (`prisma.$transaction(async (tx) => …)`) and pass `tx` to every call inside — mixing in the global client runs those queries outside the transaction.
- **Migrations in production**: review generated SQL for locking operations on big tables.
- **Large result sets**: stream or paginate instead of `findMany()` over millions of rows.

<Callout type="pitfall" title="Common mistakes">

- A new `Pool` per request (or per module import in serverless) — connection storms.
- Not releasing clients after transactions.
- Holding a transaction open across an HTTP call.
- Pool size × instances exceeding `max_connections`.
- Loops that trigger lazy loading.

</Callout>

## Explaining it in an interview

<InterviewAnswer question="How do you manage database connections in a Node service?">

I create one connection pool per process at startup and reuse it; requests borrow a connection for a query or transaction and return it, because opening connections is expensive for both sides. I size it modestly — the database can only do so much in parallel — and remember that the total is pool size times processes times replicas, which must stay under the database's connection limit; at scale, or with serverless, I put PgBouncer or RDS Proxy in front. I set connection-acquire and statement timeouts so problems fail fast, keep transactions short with no external calls inside, always release clients in `finally`, and monitor waiting counts. With ORMs I watch the generated SQL, especially for N+1 patterns, which I fix with eager loading, joins or DataLoader-style batching.

<Fragment slot="deeper">

- **What does PgBouncer's transaction mode do?** Assigns a server connection only for the duration of a transaction, multiplexing many clients.
- **Why isn't a bigger pool faster?** The database's real parallelism is limited; extra connections add contention and memory.
- **How do you detect N+1?** Query logging or APM traces showing many near-identical queries per request.

</Fragment>
</InterviewAnswer>
