**Kubernetes** (K8s) is a platform that runs containers across a cluster of machines. You don't tell it *how* to start things; you **declare the desired state** — "run three replicas of this image, reachable on this port" — and Kubernetes continuously works to make reality match: scheduling containers onto machines, restarting them when they crash, replacing them when a machine dies, and rolling out new versions. Its architecture is a **control plane** that decides and records, and **worker nodes** that run the workloads.

<Analogy>
  A thermostat. You set the desired temperature (desired state). The thermostat keeps measuring the room (actual state) and turns the heating on or off to close the gap — forever, without you issuing commands. Kubernetes is a huge set of thermostats: one for "number of replicas", one for "pods on healthy nodes", one for "endpoints of a service", and so on.
</Analogy>

## Why it matters

Kubernetes is the default platform for running services at many companies, and DevOps/backend interviews ask about its components, how a deployment actually happens, and the declarative model. Understanding the architecture makes debugging ("why is my pod Pending?") far easier.

Managed services — **EKS**, **GKE**, **AKS** — run the control plane for you; you manage nodes (or use serverless nodes like Fargate or GKE Autopilot) and your workloads.

## Declarative objects

Everything in Kubernetes is an **object** with a `spec` (desired state) and a `status` (observed state), usually written in YAML and applied with `kubectl apply`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
  labels: { app: orders-api }
spec:
  replicas: 3
  selector:
    matchLabels: { app: orders-api }
  template:
    metadata:
      labels: { app: orders-api }
    spec:
      containers:
        - name: api
          image: registry.example.com/orders-api@sha256:4b1e…
          ports: [{ containerPort: 3000 }]
```

**Labels** (key–value tags) and **selectors** are how objects find each other: a Deployment manages pods with `app: orders-api`; a Service routes to them by the same label.

## The reconciliation loop

<Diagram
  caption="Every controller repeats: observe actual state, compare with desired state, act to close the gap."
  chart={`flowchart LR
    O["observe<br/>actual: 2 pods running"] --> C{"compare with desired<br/>spec.replicas = 3"}
    C -- "gap" --> A["act<br/>create 1 pod"]
    A --> O
    C -- "match" --> W["wait for the next change"]
    W --> O`}
/>

This is why Kubernetes **self-heals**: if a pod crashes or a node disappears, actual state drifts from desired state, and controllers create replacements. You never "run a command to start 3 containers" — you change the desired state and let the loop do the work.

## Namespaces and API extension

- **Namespaces** partition a cluster for teams or environments, with their own quotas, RBAC and network policies.
- **Custom Resource Definitions (CRDs)** + **operators** extend Kubernetes with new object types and controllers (e.g. a `PostgresCluster` resource managed by a database operator, cert-manager `Certificate` objects).

<Callout type="pitfall" title="Common mistakes">

- Treating Kubernetes imperatively (`kubectl run`, manual edits) instead of declaratively from version-controlled manifests.
- Running unmanaged control planes without the expertise to operate etcd.
- Ignoring `status` and events when debugging (`kubectl describe` shows why a pod is Pending or failing).
- Over-using Kubernetes for very small systems where a managed container service (ECS, Cloud Run) would be simpler.

</Callout>

## Explaining it in an interview

<InterviewAnswer question="Explain the Kubernetes architecture.">

Kubernetes has a control plane and worker nodes. The API server is the single entry point: it authenticates, authorises and validates requests and stores objects in etcd, a Raft-replicated key-value store holding all cluster state. The scheduler assigns new pods to nodes based on resource requests and constraints, and the controller manager runs reconciliation loops — for deployments, replica sets, nodes, endpoints and so on — that continuously compare desired state in object specs with observed state and act to close the gap; a cloud controller manages load balancers and volumes. On each node, the kubelet watches for pods assigned to it, runs them through a container runtime like containerd, executes health probes and reports status, while kube-proxy or the CNI plugin handles networking. Because everything is declarative and reconciled, the cluster self-heals when pods or nodes fail.

<Fragment slot="deeper">

- **What is stored in etcd?** All Kubernetes objects and their state.
- **What does the scheduler consider?** Resource requests, node selectors/affinity, taints and tolerations, topology spread.
- **What is an operator?** A custom controller managing a custom resource, encoding operational knowledge.

</Fragment>
</InterviewAnswer>
