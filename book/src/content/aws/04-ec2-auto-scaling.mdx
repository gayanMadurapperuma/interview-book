**EC2 (Elastic Compute Cloud)** gives you virtual machines. Even if you deploy mainly to containers or Lambda, EC2 is underneath much of AWS, and its ideas — instance types, AMIs, EBS volumes, Auto Scaling groups, Spot — come up in every architecture discussion about cost and availability.

<Analogy>
  A car-rental fleet. An **instance type** is the car model (small hatchback to removal van). An **AMI** is the factory setup every car leaves with. An **Auto Scaling group** is the fleet manager who keeps "at least 3, at most 12" cars on the road, swaps out any that break down, and adds more when queues form. **Spot** is renting cars from the back lot at a huge discount, knowing they may be recalled with two minutes' notice.
</Analogy>

## Why it matters

Questions like "how do you handle a traffic spike?", "how do you replace an unhealthy server automatically?" and "how would you cut this compute bill in half?" are answered with Auto Scaling, health checks and the right pricing mix.

## Instances

| Family | Optimised for | Examples |
|---|---|---|
| General purpose | Balanced CPU/memory | `t4g`/`t3` (burstable), `m7g`/`m7i` |
| Compute optimised | CPU-heavy work | `c7g`, `c7i` — APIs, encoding, batch |
| Memory optimised | Large in-memory data | `r7g`, `x2` — caches, analytics |
| Storage optimised | High local disk IOPS | `i4i` — self-managed databases |
| Accelerated | GPUs / ML chips | `g5`, `p5`, `inf2` |

The `g` suffix means **Graviton** (AWS's ARM chips): typically ~20–40% better price-performance, and Node.js runs on ARM without changes (watch native modules).

**Storage:** **EBS** volumes are network-attached block disks in one AZ (persist independently of the instance, snapshot to S3). **Instance store** is fast local disk that is lost when the instance stops. **EFS** is a shared NFS file system across AZs.

**AMI** (Amazon Machine Image): the OS image the instance boots from. Bake your own ("golden AMI") for fast, consistent startup, or use **user data** scripts to configure at boot.

## Auto Scaling groups

An **Auto Scaling group (ASG)** keeps a fleet between `min` and `max`, aiming for `desired`, spread across AZs, using a **launch template** (AMI, instance type, security groups, IAM instance profile, user data).

| Scaling policy | How it works | Good for |
|---|---|---|
| **Target tracking** | Keep a metric at a target, e.g. average CPU 50% or ALB requests per target 1000 | The default choice |
| **Step scaling** | Add/remove N instances when an alarm crosses thresholds | Fine-grained control |
| **Scheduled** | Change capacity at set times | Known daily peaks |
| **Predictive** | Forecasts from history and scales ahead | Regular cyclical traffic |

**Health checks:** by default the ASG uses EC2 status checks (is the VM alive?). Enable **ELB health checks** on the group so an instance whose app is broken — but whose VM is fine — gets replaced too.

**Lifecycle hooks** pause launch or termination so you can run setup or drain work (finish jobs, push logs) first. **Instance refresh** rolls a new launch template across the fleet gradually.

## Pricing options

| Option | Discount | Trade-off | Use for |
|---|---|---|---|
| On-demand | — | Flexible, no commitment | Spiky or unknown load |
| Savings Plans / Reserved | up to ~72% | 1–3 year commitment | Steady baseline |
| Spot | up to ~90% | Can be reclaimed with 2 min notice | Stateless workers, batch, CI, part of a web fleet |

A common pattern is a **mixed-instances ASG**: a Savings-Plan-covered on-demand base plus Spot across several instance types for the rest, with capacity rebalancing.

<Callout type="pitfall" title="Common mistakes">

- Storing state (uploads, sessions) on an instance's disk — it disappears with scale-in.
- ASG relying only on EC2 status checks, so broken apps keep receiving traffic.
- Slow boot (installing everything in user data) making scale-out too late for spikes — bake an AMI or use containers.
- All capacity in one AZ, or a `max` too low to absorb a spike.
- SSH keys and port 22 open to the world instead of using **Session Manager**.

</Callout>

## Explaining it in an interview

<InterviewAnswer question="How do you make an EC2-based service scale and heal itself?">

I put the instances in an Auto Scaling group behind an Application Load Balancer, spread across at least two AZs, launched from a launch template with a pre-baked AMI so new instances start quickly. The servers are stateless: sessions in Redis or DynamoDB, files in S3. I use a target-tracking policy on CPU or requests per target, so the group adds instances when the metric rises above target and removes them when it falls, with warm-up so it doesn't overshoot and connection draining on scale-in. I enable ELB health checks on the group so an instance whose app stops responding is terminated and replaced, not just one whose VM dies. For cost I'd cover the steady baseline with a Savings Plan and run the burst capacity on a mix of Spot instance types, and I'd use Graviton instances where the app supports ARM.

<Fragment slot="deeper">

- **EBS vs instance store?** Persistent network disk in one AZ vs fast ephemeral local disk.
- **How do you deploy a new version?** Instance refresh or blue/green with a new ASG and target group — or move to containers.
- **What happens when Spot is reclaimed?** A 2-minute interruption notice; the ASG launches replacement capacity, so the app must tolerate losing an instance.

</Fragment>
</InterviewAnswer>
