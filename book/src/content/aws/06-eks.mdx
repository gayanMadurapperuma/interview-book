**Amazon EKS (Elastic Kubernetes Service)** runs the Kubernetes **control plane** for you — API server and etcd, highly available across three AZs, patched and backed up by AWS. You still own the **data plane** (the nodes your pods run on) and everything you install into the cluster. The Kubernetes concepts are covered in the Kubernetes volume. This chapter is about the AWS-specific parts interviewers probe: how pods get VPC IPs, how traffic reaches them, how pods get IAM permissions, how nodes scale, and how you upgrade without downtime.

<Analogy>
  Renting a fully staffed airport control tower (the **control plane**) while you bring your own planes and ground crew (the **nodes** and add-ons). AWS keeps the tower running and radios working in all weathers. You decide how many planes to buy or lease, how they're maintained, and which gates they use. **Karpenter** is a fleet manager who leases exactly the right plane for each new flight and returns it when it's done.
</Analogy>

## Why it matters

Many companies standardise on Kubernetes, so "how would you run this on EKS?", "how does a pod get permission to read S3?", "why are we running out of IP addresses?" and "how do you upgrade a cluster?" are common senior-level questions.

## What AWS manages vs what you manage

| AWS manages | You manage |
|---|---|
| API server, etcd, scheduler, controller manager — multi-AZ, scaled, patched | Worker nodes (unless using Fargate or EKS Auto Mode): AMIs, patching, scaling |
| Control-plane version upgrades (when you trigger them) | Upgrading nodes and add-ons to match, and API deprecations in your manifests |
| Integration points: IAM auth, VPC networking, ELB and EBS integrations | Installing and configuring add-ons (CNI, CoreDNS, ingress, autoscaler, observability) |
| | Workload security: RBAC, network policies, pod security, image provenance |

## Compute options for the data plane

| Option | What it is | Use when |
|---|---|---|
| **Managed node groups** | EKS-managed ASGs of EC2 with EKS-optimised AMIs (AL2023 / Bottlerocket); managed rolling updates | Predictable, simple node pools |
| **Karpenter** | Open-source autoscaler that watches pending pods and launches the cheapest instances that fit, directly (no ASGs); consolidates under-used nodes | Most production clusters: fast scaling, Spot + Graviton mixes, bin-packing |
| **Fargate profiles** | Each pod runs in its own micro-VM; no nodes at all | Small or bursty workloads, strong isolation; no DaemonSets, GPUs or EBS |
| **EKS Auto Mode** | AWS runs Karpenter, CNI, load balancing, storage and node patching for you | Teams that want "Kubernetes API, fewer moving parts" |
| **Self-managed nodes** | Your own ASGs and AMIs | Special OS or hardware needs |

## Pod networking: the VPC CNI

The **Amazon VPC CNI** gives every pod a **real IP address from your subnet** (via secondary IPs on the node's ENIs). Pods are first-class VPC citizens: security groups, VPC flow logs, and load balancers can target pod IPs directly.

The trade-off is **IP exhaustion**: a `/24` subnet has ~250 addresses, and a busy node can consume dozens. Mitigations:

- Size subnets generously (`/19` or larger for pods), or add a secondary CIDR (`100.64.0.0/10`) with **custom networking** so pods use separate subnets.
- **Prefix delegation** assigns `/28` prefixes to ENIs, raising pods per node and speeding allocation.
- **IPv6 clusters** remove the problem entirely.
- **Security groups for pods** apply VPC security groups to individual pods (e.g. only the `payments` pods may reach the payments database).

Inside the cluster you still use Kubernetes `NetworkPolicy` (the VPC CNI can enforce it) for pod-to-pod rules.

## Getting traffic in: AWS Load Balancer Controller

The **AWS Load Balancer Controller** watches Kubernetes objects and creates AWS load balancers:

- `Ingress` (class `alb`) → an **ALB** with path/host rules, ACM certificates, WAF, and **target type `ip`** to route straight to pod IPs (no extra NodePort hop).
- `Service` of type `LoadBalancer` → an **NLB** for TCP/UDP or static IPs.
- `IngressGroup` lets many Ingresses share one ALB to save cost.
- **ExternalDNS** creates Route 53 records for them; **cert-manager** or ACM for TLS.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: orders
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/group.name: public
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:eu-west-1:123456789012:certificate/…
    alb.ingress.kubernetes.io/healthcheck-path: /readyz
spec:
  ingressClassName: alb
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /orders
            pathType: Prefix
            backend: { service: { name: orders, port: { number: 80 } } }
```

## IAM for pods: Pod Identity and IRSA

Pods must never use the node's instance role (every pod on the node would share it). Two ways to give **one service account** its own IAM role:

- **EKS Pod Identity** (newer, simpler) — install the Pod Identity agent add-on, then create an *association* between a namespace/service account and a role. Roles don't need cluster-specific trust policies, so they're reusable across clusters.
- **IRSA (IAM Roles for Service Accounts)** — the cluster's OIDC provider issues a projected service-account token; the SDK exchanges it via `sts:AssumeRoleWithWebIdentity`. Works everywhere, including non-EKS clusters.

## Cluster access for humans and CI

- **Access entries** (the EKS API) map IAM principals (SSO roles, CI roles) to Kubernetes permissions, using AWS-managed access policies or Kubernetes groups for RBAC. They replace the fragile `aws-auth` ConfigMap.
- Make the API endpoint **private** (or public with restricted CIDRs) and reach it through VPN/SSO or CI runners in the VPC.
- Prefer **GitOps** (Argo CD / Flux running inside the cluster) so humans and CI rarely need write access at all.

## Storage

- **EBS CSI driver** — `PersistentVolume`s backed by EBS (gp3). Volumes are **zonal**: a StatefulSet pod is pinned to its volume's AZ (use `WaitForFirstConsumer`).
- **EFS CSI driver** — shared `ReadWriteMany` file storage across AZs.
- **Mountpoint for S3 CSI** — mount buckets for read-heavy data (ML models, assets).
- Prefer managed data services (Aurora, DynamoDB, ElastiCache, MSK) over running stateful databases in the cluster.

## Add-ons and upgrades

**Managed add-ons** (VPC CNI, CoreDNS, kube-proxy, EBS CSI, Pod Identity agent, ADOT) are versioned and updated by EKS. Kubernetes releases come roughly three times a year, and each EKS version has ~14 months of standard support (extended support costs extra), so **upgrades are routine work**:

1. Check deprecated APIs in your manifests and Helm charts (EKS **upgrade insights**, `pluto`, `kubent`).
2. Upgrade the **control plane** one minor version at a time (in-place, managed by AWS).
3. Update **managed add-ons** to compatible versions.
4. Roll the **nodes**: managed node groups update rolling; Karpenter replaces nodes via drift detection. PodDisruptionBudgets keep services available.
5. For risky jumps, **blue/green clusters**: build a new cluster with GitOps, shift traffic with Route 53 weights or ALB target groups, then retire the old one.

<Callout type="pitfall" title="Common mistakes">

- Pods using the node instance role, so every pod can do what any pod can.
- Small pod subnets, leading to `failed to assign an IP address` errors at scale.
- Falling several versions behind and paying for extended support, then facing a multi-step upgrade.
- No PodDisruptionBudgets, so node drains during upgrades or consolidation take whole services down.
- Running everything with cluster-admin through the old `aws-auth` ConfigMap.
- Running databases in the cluster without the operational maturity to back up, upgrade and fail them over.

</Callout>

## Explaining it in an interview

<InterviewAnswer question="How would you run a production Kubernetes platform on AWS with EKS?">

EKS gives me a managed, multi-AZ control plane, so my job is the data plane and the platform add-ons. I'd create the cluster with Terraform in private subnets across three AZs, with a private API endpoint and access entries mapping SSO and CI roles to RBAC. Nodes are provisioned by Karpenter, with NodePools mixing Graviton and Spot for stateless workloads and on-demand for critical ones, and consolidation to keep utilisation high. The VPC CNI gives pods real VPC IPs, so I'd size pod subnets generously or use prefix delegation or a secondary CIDR to avoid IP exhaustion. Traffic comes in through the AWS Load Balancer Controller, creating an ALB with IP targets plus WAF and ACM certificates, and ExternalDNS for Route 53. Each service account gets its own IAM role through Pod Identity, never the node role, and secrets come from Secrets Manager via the External Secrets Operator. Stateful data lives in managed services like Aurora and DynamoDB. Deployments go through GitOps with Argo CD. I keep up with Kubernetes versions by upgrading the control plane, then add-ons, then rolling nodes with PodDisruptionBudgets, or by blue/green clusters for big jumps.

<Fragment slot="deeper">

- **Pod Identity vs IRSA?** Pod Identity needs no OIDC trust per cluster and is simpler to manage; IRSA works on any cluster and older setups.
- **Karpenter vs Cluster Autoscaler?** Karpenter launches right-sized instances directly and consolidates; Cluster Autoscaler scales predefined node groups.
- **Why target type ip?** The ALB sends to pod IPs directly, skipping the NodePort hop and enabling accurate health checks.

</Fragment>
</InterviewAnswer>
