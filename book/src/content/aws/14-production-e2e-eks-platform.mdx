This chapter brings the whole volume together in one realistic system: **a global e-commerce platform built from Node.js microservices running on EKS**, using the AWS services around the cluster for everything stateful, secure and observable. It is the shape of answer expected for "design and operate X in production on AWS": not just the boxes, but how the platform is built, how code gets to production safely, how it is secured and observed, and what happens when an AZ or a whole region fails.

<Analogy>
  A large shopping mall. The **landing zone** is the mall's legal structure and building codes: separate units for shops, security and management. The **edge** is the entrances with guards and signposts (CloudFront, WAF, Route 53). The **EKS platform** is the managed floor space with power, plumbing and fire alarms already installed (add-ons) so shops (services) just move in. The **event backbone** is the internal delivery corridor. **GitOps** is the rule that no shop changes its layout unless the change is in the approved floor plan. **DR** is a second mall in another city kept stocked and ready to open.
</Analogy>

## The scenario and requirements

**Product:** an online store — catalog and search, cart, checkout and payments, orders, inventory, notifications, analytics. About 12 Node.js services built by 6 teams.

| Requirement | Target |
|---|---|
| Traffic | 3k RPS normal, **15k RPS** during sales; spiky |
| Latency | p99 under 300 ms for browse and cart APIs |
| Availability | **99.95%** for checkout |
| Data loss / recovery | RPO ≤ 1 min, RTO ≤ 15 min for a full region loss |
| Compliance | Card data via a PCI-compliant provider (tokenised); GDPR for EU customers |
| Teams | Independent deploys many times a day, no shared release train |

Stating these first drives every choice below: spiky traffic → autoscaling at both pod and node level; 99.95% plus RTO 15 min → multi-AZ everywhere plus a warm standby region; many teams → a self-service platform with GitOps and guardrails.

## 1. Multi-account landing zone

Accounts are the strongest isolation boundary on AWS (blast radius, IAM, quotas, billing). The platform starts with **AWS Organizations + Control Tower**:

  caption="Multi-account layout. Workloads are isolated per environment; security, logging, networking and shared tooling each live in their own account, governed by SCP guardrails."
  chart={`flowchart TB

- **SSO (IAM Identity Center)** for all humans: read-only by default, break-glass admin with approval.
- **SCPs**: deny leaving approved regions, deny disabling CloudTrail/GuardDuty/Config, deny creating IAM users and access keys, deny public S3.
- **Networking account**: Transit Gateway connects workload VPCs; centralised egress through NAT + Network Firewall; private Route 53 zones shared.
- **Shared services account**: ECR (replicated to both prod regions), CI runners, the Argo CD management cluster.
- Everything created with **Terraform** (Account Factory for Terraform for new accounts).

| Layer | Choice | Why |
|---|---|---|
| DNS | Route 53, latency-based records + health checks per region | Users go to the nearest healthy region |
| Edge | CloudFront + **WAF** (managed rules, rate limits, bot control) + **Shield** | Caches static and catalog responses, absorbs DDoS, terminates TLS near users |
| Static frontend | Next.js static assets in S3 behind CloudFront (OAC) | No servers for static content |
| Ingress | One shared ALB via `IngressGroup`, target type `ip`, ACM certs | Path routing to services, direct-to-pod |
| Services | Node.js on EKS, one namespace per team | Independent deploys and scaling |
| Data | **Database per service**: Aurora PostgreSQL (orders), DynamoDB (cart, payments idempotency), OpenSearch (search), ElastiCache Redis (sessions, caching, rate limits), S3 (images, exports) | Each data store fits its access pattern; no shared schema between teams |

Service-to-service calls inside the cluster go through Kubernetes Services (optionally a mesh such as Istio Ambient or VPC Lattice for mTLS and traffic policy), always with **timeouts, retries with jitter and circuit breakers**.

## 3. The event backbone

Checkout must not call inventory, email and analytics synchronously. Orders publish domain events; consumers react independently.

<Diagram

- **Transactional outbox**: the order row and an `outbox` row are written in the same Aurora transaction; a relay (Debezium on MSK Connect) publishes to Kafka. No dual-write inconsistency.
- **MSK (Kafka)** for ordered, replayable, high-volume events, partitioned by `orderId`. (A smaller platform would use EventBridge + SQS, as in the messaging chapter.)
- Consumers are **idempotent** (processed-event IDs in DynamoDB with TTL) with **dead-letter topics**.
- The checkout workflow (reserve stock → charge → confirm, with compensations) is a **saga**, orchestrated by Step Functions or by the orders service.
- Consumer pods autoscale on **Kafka consumer lag** with **KEDA**.

## 4. Building the EKS platform

Infrastructure is layered so each layer changes at its own pace:

| Layer | Tool | Contents |
|---|---|---|
| 0. Accounts & guardrails | Terraform + Control Tower | Accounts, SCPs, SSO, log archive |
| 1. Network | Terraform | VPC per region, 3 AZs, public / private / pod / data subnets (large pod CIDR), TGW attachment, endpoints |
| 2. Data | Terraform | Aurora Global Database, DynamoDB global tables, MSK, OpenSearch, ElastiCache, KMS keys |
| 3. Cluster | Terraform (`terraform-aws-eks`) | EKS cluster (private endpoint), access entries, managed add-ons, Karpenter IAM and a small system node group |
| 4. Platform add-ons | Argo CD (app-of-apps, Helm) | Everything installed *into* the cluster, below |
| 5. Applications | Argo CD + Argo Rollouts | Each team's services from their config repos |

Platform add-ons, all managed by GitOps:

| Need | Add-on |
|---|---|
| Node provisioning | **Karpenter** (NodePools: `system` on-demand, `general` Graviton Spot + on-demand fallback) |
| Ingress & DNS | **AWS Load Balancer Controller**, **ExternalDNS**, ACM |
| Secrets | **External Secrets Operator** syncing from Secrets Manager |
| Pod IAM | **EKS Pod Identity** agent; one role per service account |
| Autoscaling | HPA on CPU / RPS, **KEDA** on Kafka lag and SQS depth |
| Progressive delivery | **Argo Rollouts** (canary with automated analysis) |
| Policy | **Kyverno**: require resources, probes, non-root, signed images from our ECR only |
| Observability | **ADOT collector** (metrics → Amazon Managed Prometheus, traces → X-Ray), **Fluent Bit** (logs → CloudWatch / OpenSearch) |
| Backup | **Velero** for cluster objects (state lives in managed services anyway) |

## 5. Deploying the application

Each service ships a Helm chart. What makes it production-ready:

```yaml
# orders: key parts of the production manifests (rendered from Helm)
apiVersion: argoproj.io/v1alpha1
kind: Rollout                     # Argo Rollouts instead of a plain Deployment
metadata: { name: orders, namespace: orders }
spec:
  replicas: 6
  selector: { matchLabels: { app: orders } }
  strategy:
    canary:
      steps:
        - setWeight: 10
        - analysis: { templates: [{ templateName: success-rate-and-latency }] }
        - setWeight: 50
        - pause: { duration: 5m }
  template:
    metadata: { labels: { app: orders } }
    spec:
      serviceAccountName: orders          # Pod Identity → orders-role (Aurora IAM auth, its S3 prefix)
      topologySpreadConstraints:
        - { maxSkew: 1, topologyKey: topology.kubernetes.io/zone, whenUnsatisfiable: DoNotSchedule, labelSelector: { matchLabels: { app: orders } } }
      containers:
        - name: api
          image: 111122223333.dkr.ecr.eu-west-1.amazonaws.com/orders@sha256:4f1c…   # pinned digest, signed
          ports: [{ containerPort: 3000 }]
          resources: { requests: { cpu: 500m, memory: 512Mi }, limits: { memory: 512Mi } }
          envFrom: [{ secretRef: { name: orders-db } }]      # created by External Secrets
          readinessProbe: { httpGet: { path: /readyz, port: 3000 }, periodSeconds: 5 }
          livenessProbe:  { httpGet: { path: /livez,  port: 3000 }, periodSeconds: 10 }
          lifecycle: { preStop: { sleep: { seconds: 10 } } }  # let the ALB deregister before SIGTERM handling
          securityContext: { runAsNonRoot: true, readOnlyRootFilesystem: true, allowPrivilegeEscalation: false }
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: orders, namespace: orders }
spec: { minAvailable: 4, selector: { matchLabels: { app: orders } } }
---
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata: { name: orders-db, namespace: orders }
spec:
  secretStoreRef: { kind: ClusterSecretStore, name: aws-secrets-manager }
  target: { name: orders-db }
  dataFrom: [{ extract: { key: prod/orders/db } }]
```

## 6. Security in layers

| Layer | Controls |
|---|---|
| Organisation | SCP guardrails, SSO only, no IAM users, separate prod accounts |
| Edge | WAF managed rules, rate limiting, bot control, Shield, TLS 1.2+ |
| Network | Private subnets; private EKS endpoint; security groups for pods (only payments pods reach the payments store); NetworkPolicies default-deny; egress through Network Firewall |
| Identity | Pod Identity per service account; least-privilege roles; Aurora IAM auth |
| Supply chain | Signed images, SBOMs, ECR scanning, Kyverno admission (signed + our registry only), pinned digests |
| Runtime | Non-root, read-only root FS, no privilege escalation; GuardDuty EKS runtime monitoring |
| Data | KMS customer-managed keys for Aurora, DynamoDB, S3, EBS and EKS secrets envelope encryption; card data never stored (provider tokens) |
| Audit & detection | Org-wide CloudTrail to the log archive, Config rules, Security Hub, alerts to the security team |

## 7. Observability

- **Metrics**: ADOT / Prometheus scraping → **Amazon Managed Prometheus**; **Amazon Managed Grafana** dashboards per service (RED: rate, errors, duration) and per platform component.
- **Traces**: OpenTelemetry SDK in each Node.js service → ADOT → X-Ray, with trace IDs in every log line.
- **Logs**: structured JSON → Fluent Bit → CloudWatch Logs (30-day retention) and S3 for long-term.
- **SLOs and alerting**: SLOs per user journey (browse, add to cart, checkout) with **burn-rate alerts** to PagerDuty; Container Insights for cluster health; Kafka lag and DLQ alarms.
- **Business metrics**: orders per minute and payment success rate, often the fastest signal that something is wrong.

## 8. Resilience and disaster recovery

**Within a region (AZ failure):** three AZs; topology spread keeps pods in every AZ; Karpenter replaces lost capacity; Aurora fails over to a reader in under ~30 s; DynamoDB, S3, MSK and the ALB are multi-AZ already. Result: a brief blip, no manual action.

- The standby region runs the **same platform from the same Git repos** (Argo CD), scaled down; Karpenter scales it up on failover.
- **Aurora Global Database** (managed failover/switchover promotes the secondary in about a minute); **DynamoDB global tables**; **S3 Cross-Region Replication**; ECR replication; MSK replicated with MirrorMaker 2 / MSK Replicator.
- Failover: Route 53 health checks shift traffic; a runbook (or **ARC**, Application Recovery Controller) promotes Aurora, then scales the standby. Rehearse with **game days** and **AWS Fault Injection Service** (AZ power loss, node termination, latency injection).

| Strategy | RTO | Cost | Chosen? |
|---|---|---|---|
| Backup & restore | hours | lowest | for dev/staging |
| Pilot light | tens of minutes | low | — |
| **Warm standby** | **minutes** | medium | **prod: meets RTO 15 min** |
| Multi-region active-active | ~zero | highest; needs conflict handling | future, for browse traffic only |

## 9. Cost

- Karpenter with **Graviton + Spot** for stateless services (on-demand fallback; PDBs + interruption handling) and consolidation to keep node utilisation high.
- **Compute Savings Plans** for the on-demand baseline (covers EC2, Fargate and Lambda).
- Right-sized pod requests (Goldilocks / VPA recommendations), since requests drive node count.
- CloudFront caching for catalog reads; VPC endpoints instead of NAT for S3, DynamoDB and ECR; log retention and sampling for traces.
- Per-team cost allocation with namespace labels + **split cost allocation data** for EKS in Cost Explorer; budgets and anomaly detection.

## 10. Day-2 operations

- **Cluster upgrades** every ~4 months: staging first, then control plane → add-ons → Karpenter drift-replaces nodes, guarded by PDBs. For risky jumps, **blue/green clusters** behind Route 53 weights.
- **Capacity events** (Black Friday): pre-scale with scheduled minimums, warm Aurora readers, raise service quotas in advance, load-test with production-like data.
- **Incidents**: SLO alert → runbook → rollback is one Git revert (or an automatic canary abort) → blameless post-incident review.
- **Tenancy**: namespaces, ResourceQuotas and LimitRanges per team; a golden-path Helm chart and templates so teams get probes, PDBs, Pod Identity and dashboards by default.

<Callout type="pitfall" title="Where production platforms usually go wrong">

- One giant shared database, so teams can't deploy independently and one bad query takes everyone down.
- CI pipelines holding cluster-admin credentials instead of GitOps pull.
- No PDBs or topology spread, so a node drain or AZ loss removes a whole service.
- A DR region that was never tested: stale images, missing secrets, wrong quotas.
- Synchronous call chains through checkout, so an email-service outage blocks payments.
- Unbounded log and metrics cardinality quietly becoming the largest line on the bill.

</Callout>

## Explaining it in an interview

<InterviewAnswer question="Design and operate a large e-commerce platform on AWS using Kubernetes. Walk me through it end to end.">

I'd start from requirements: spiky traffic up to 15k RPS, p99 under 300 ms, 99.95% for checkout, RPO about a minute and RTO 15 minutes, and six teams deploying independently. The foundation is a multi-account landing zone with Control Tower: separate dev, staging and prod accounts, a log archive, security tooling, networking and shared-services accounts, SSO for people and SCP guardrails. The request path goes Route 53 latency routing to CloudFront with WAF and Shield, then a shared ALB created by the Load Balancer Controller, routing by path directly to pod IPs on EKS in three AZs. Each service owns its data — Aurora PostgreSQL for orders, DynamoDB for carts and idempotency, OpenSearch for search, Redis for caching — and side effects go through events: a transactional outbox to MSK, idempotent consumers, KEDA scaling them on lag, and a saga for checkout. The platform is Terraform for accounts, network, data and the cluster, then Argo CD installs add-ons: Karpenter on Graviton and Spot, External Secrets from Secrets Manager, Pod Identity per service account, Kyverno policies, ADOT and Fluent Bit. Delivery is GitOps: CI builds, scans and signs arm64 images, pushes to ECR via OIDC and bumps a digest in the config repo, then Argo Rollouts canaries at 10% with automated Prometheus analysis and auto-rollback. Security is layered from SCPs to signed images, network policies, security groups for pods and KMS everywhere. Observability is Managed Prometheus, Grafana, X-Ray and SLO burn-rate alerts. AZ failures are absorbed automatically, and for regional failure there's a warm standby in a second region with Aurora Global Database and DynamoDB global tables, the same GitOps state, and Route 53 failover, rehearsed with Fault Injection Service game days.

<Fragment slot="deeper">

- **Why EKS over ECS here?** Many teams, a rich add-on ecosystem (Argo, KEDA, Kyverno), portability and existing Kubernetes skills. ECS would be simpler for a smaller org.
- **Why MSK rather than EventBridge?** Ordered, replayable, high-throughput streams and CDC via Debezium. EventBridge + SQS is simpler at lower volume.
- **How do you keep the DR region from drifting?** Same Git source of truth, continuous deploys to both regions, and regular failover drills.

</Fragment>
</InterviewAnswer>
