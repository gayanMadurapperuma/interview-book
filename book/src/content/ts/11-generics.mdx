**Generics** let you write a function, class, interface or type alias that works with **many types** while preserving the connection between them. Instead of `any` — which throws type information away — a type parameter like `T` is a placeholder filled in at each use: `Array<string>`, `Promise<User>`, `Map<string, Order[]>`. **Constraints** (`T extends …`) say what a type parameter must support, and **defaults** make common cases shorter.

<Analogy>
  A generic is a labelled storage box design: "Box of ___". Make a Box of books and the label says books; anything you take out is a book. With `any` you'd have a box marked "stuff" — you'd have to check every item you pulled out. A constraint is a box design that only accepts things with handles, because the design relies on carrying them by the handle.
</Analogy>

## Why it matters

Generics are everywhere in TypeScript — built-in types, React props, repositories, API clients. Interviewers ask you to write generic functions, explain constraints, and fix "Type 'T' is not assignable to…" errors.

## Generic functions

```ts
function identity<T>(value: T): T { return value; }
identity(42);            // T = number → returns number
identity('hi');          // T = string

function last<T>(items: readonly T[]): T | undefined { return items.at(-1); }

function mapValues<K extends string, A, B>(obj: Record<K, A>, fn: (a: A) => B): Record<K, B> {
  const out = {} as Record<K, B>;
  for (const k in obj) out[k] = fn(obj[k]);
  return out;
}
mapValues({ a: 1, b: 2 }, (n) => String(n));   // Record<'a' | 'b', string>
```

Type arguments are almost always **inferred** from the arguments; write them explicitly (`identity<string>(x)`) only when inference can't work them out.

## Constraints

Without a constraint, you can only do with `T` what's valid for every possible type — almost nothing.

```ts
function getLength<T>(x: T) { return x.length; }               // ✘ 'length' doesn't exist on T

function getLength2<T extends { length: number }>(x: T) {       // ✓ only types with length
  return x.length;
}
getLength2('abc'); getLength2([1, 2]); getLength2(42);           // last one ✘
```

### `keyof` constraints: typed property access

```ts
function pick<T extends object, K extends keyof T>(obj: T, keys: K[]): Pick<T, K> {
  const out = {} as Pick<T, K>;
  for (const k of keys) out[k] = obj[k];
  return out;
}

const user = { id: 1, name: 'Ada', email: 'ada@x.com' };
pick(user, ['id', 'name']);      // { id: number; name: string }
pick(user, ['password']);        // ✘ 'password' is not a key of user
```

## Generic interfaces, types and classes

```ts
interface ApiResponse<T> { data: T; meta: { requestId: string } }
type Paginated<T> = { items: T[]; nextCursor: string | null };

interface Repository<T extends { id: ID }, ID = string> {   // default type parameter
  findById(id: ID): Promise<T | undefined>;
  save(entity: T): Promise<T>;
}

class InMemoryRepo<T extends { id: string }> implements Repository<T> {
  private items = new Map<string, T>();
  async findById(id: string) { return this.items.get(id); }
  async save(e: T) { this.items.set(e.id, e); return e; }
}

class TypedEmitter<Events extends Record<string, unknown[]>> {
  on<E extends keyof Events>(event: E, fn: (...args: Events[E]) => void) { /* … */ }
  emit<E extends keyof Events>(event: E, ...args: Events[E]) { /* … */ }
}
const bus = new TypedEmitter<{ orderPlaced: [orderId: string, total: number] }>();
bus.emit('orderPlaced', 'o1', 50);      // ✓
bus.emit('orderPlaced', 'o1');          // ✘ missing total
```

## Good generic design

- A type parameter should appear **at least twice** (connecting inputs and outputs). `function log<T>(x: T): void` is just `(x: unknown) => void`.
- Prefer **constraints over casts**.
- Keep the number of type parameters small; name them meaningfully when there are several (`TKey`, `TValue`).
- Use `readonly T[]` for inputs you don't mutate — it accepts both mutable and readonly arrays.

## Generics vs `any` vs `unknown` vs overloads

| Tool | Keeps type info? | Safe? | Use |
|---|---|---|---|
| `any` | no | no | escape hatch only |
| `unknown` | no | yes (must narrow) | truly unknown input |
| union | partly | yes | small fixed set of types |
| generic | **yes**, and relationships | yes | functions that work for any type consistently |
| overloads | per signature | yes | different input→output mappings |

<Callout type="pitfall" title="Common mistakes">

- Using `any` where a generic would preserve the type.
- Unused or single-use type parameters.
- Casting `as T` inside implementations to silence errors that a constraint should solve.
- Over-generic code that is hard to read and gives poor error messages.

</Callout>

## Explaining it in an interview

<InterviewAnswer question="What are generics and why use them instead of any?">

Generics are type parameters: placeholders filled in at each use, usually inferred from the arguments. They let one function, class or interface work for many types while preserving the relationships between them — `first<T>(items: T[]): T | undefined` returns a `number` for numbers and a `User` for users, whereas `any` would lose that and switch off checking. Constraints like `T extends { length: number }` or `K extends keyof T` say what operations are allowed and let me write things like a typed `pick` whose return type contains exactly the chosen properties. I use them for repositories, API response wrappers, typed event emitters and utilities, keeping each type parameter meaningful — if it appears only once, it isn't needed.

<Fragment slot="deeper">

- **What does `K extends keyof T` mean?** K must be one of T's property names.
- **What is a default type parameter?** A fallback type when none is given or inferred: `<ID = string>`.
- **Why `readonly T[]` for parameters?** Accepts both mutable and readonly arrays and documents no mutation.

</Fragment>
</InterviewAnswer>
