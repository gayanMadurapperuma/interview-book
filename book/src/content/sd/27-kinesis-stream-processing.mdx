**Amazon Kinesis Data Streams** is AWS's managed, Kafka-like streaming service: producers write records into a **stream** made of **shards**; records are ordered within a shard and retained (24 hours by default, up to a year) so several consumers can read and replay. **Kinesis Data Firehose** (now Amazon Data Firehose) delivers streams into S3, Redshift or OpenSearch with batching and format conversion and no code. On top of streams sits **stream processing** — computing results continuously over never-ending data with tools like Apache Flink, Kafka Streams or Spark Structured Streaming.

<Analogy>
  A batch job is reading yesterday's newspaper and summarising it. Stream processing is a sports commentator: events keep arriving, the commentator keeps a running tally (state), talks about "the last five minutes" (windows), and has to decide how long to wait for a late replay before calling the score final (watermarks).
</Analogy>

## Why it matters

Real-time analytics, fraud detection, live dashboards, IoT, clickstreams and log pipelines all rely on streams. Interviewers ask Kinesis vs Kafka vs SQS, how shards scale, and stream-processing concepts like windowing and late data.

| Concept | Kinesis | Kafka equivalent |
|---|---|---|
| Stream | stream | topic |
| Shard | 1 MB/s or 1,000 records/s write, 2 MB/s read | partition |
| Partition key | hashed to a shard | record key |
| Sequence number | position in shard | offset |
| Checkpoint | stored by KCL (DynamoDB) or Lambda | committed offset |
| Retention | 24 h – 365 days | configurable |

- **Capacity**: provisioned (you choose shard count, resharding by split/merge) or **on-demand** (scales automatically).
- **Fan-out**: shared read throughput is 2 MB/s per shard across all consumers; **enhanced fan-out** gives each consumer its own 2 MB/s with push delivery.
- **Hot shards**: a skewed partition key overloads one shard → `ProvisionedThroughputExceeded`. Use high-cardinality keys.
- **Lambda** consumers process per shard in order; configure batch size, parallelization factor, bisect-on-error and a failure destination.

## Kinesis vs Kafka vs SQS

| | Kinesis Data Streams | Kafka / MSK | SQS |
|---|---|---|---|
| Model | sharded replayable log | partitioned replayable log | queue |
| Ops | fully managed, serverless option | self-run or MSK (still cluster-shaped) | fully managed |
| Throughput unit | shard (1 MB/s in) | partition (much higher) | effectively unlimited |
| Ecosystem | AWS-native (Lambda, Firehose, Flink) | huge (Connect, Streams, Schema Registry) | AWS-native |
| Choose when | AWS-only, moderate scale, minimal ops | high throughput, portability, rich ecosystem | jobs and buffering, no replay |

### Event time vs processing time

- **Processing time**: when the system sees the event. Easy, but results change if processing is delayed.
- **Event time**: when the event actually happened (a timestamp in the event). Correct, but events arrive **late** and **out of order** (mobile devices offline, network delays).

### Watermarks and late data

A **watermark** is the processor's estimate that "all events up to time T have probably arrived". When the watermark passes a window's end, the window's result is emitted. Late events after that can be dropped, sent to a side output, or used to update the result (allowed lateness).

### State and exactly-once

Stream processors keep **state** (counts, joins, sessions) in local stores, periodically **checkpointed** to durable storage (Flink snapshots to S3). On failure they restore the last checkpoint and replay the stream from the matching offsets — together giving **exactly-once state** updates. Sinks must be idempotent or transactional for end-to-end exactly-once.

<Callout type="pitfall" title="Common mistakes">

- Low-cardinality partition keys → hot shards.
- Using processing time when results must reflect when events happened.
- No plan for late or duplicate events.
- Lambda consumers that fail a whole batch forever, blocking the shard ("poison pill") — use bisect-on-error and failure destinations.
- Treating a stream as a database to query ad hoc.

</Callout>

## Explaining it in an interview

<InterviewAnswer question="How would you build real-time analytics on a stream of events?">

I'd ingest events into a partitioned, replayable stream — Kinesis Data Streams on AWS, or Kafka — keyed by a high-cardinality ID so shards stay balanced and per-entity order is kept. A stream processor such as Flink computes results continuously using event time, not arrival time, with tumbling or sliding windows and watermarks that decide when a window is complete while tolerating some lateness; very late events go to a side output. It keeps state in local stores checkpointed to S3, so on failure it restores and replays for exactly-once state. Results go to a low-latency store for dashboards, and in parallel Firehose writes the raw stream to S3 as Parquet for historical queries. Consumers and sinks are idempotent because delivery is at-least-once.

<Fragment slot="deeper">

- **Shard limits?** About 1 MB/s or 1,000 records/s in, 2 MB/s out per shard (shared unless enhanced fan-out).
- **Event time vs processing time?** When it happened vs when we saw it; event time needs watermarks.
- **What is a watermark?** A progress marker asserting no earlier events are expected (within tolerance).

</Fragment>
</InterviewAnswer>
