**Scalability** is a system's ability to handle more load by adding resources. You can scale **vertically** (a bigger machine) or **horizontally** (more machines). Horizontal scaling works best when servers are **stateless** — any server can handle any request, because nothing about a user's session lives only in one server's memory. But scaling is never perfectly linear: **Amdahl's Law** and the **Universal Scalability Law** explain why adding the hundredth server helps far less than the second — and sometimes makes things worse.

<Analogy>
  A pizza restaurant getting busier. Vertical scaling is buying a bigger oven. Horizontal scaling is opening more identical kitchens. That only works if any kitchen can make any order — the recipes aren't in one chef's head (statelessness). And no matter how many kitchens you open, if every order must be approved by the one manager on the phone, that manager becomes the limit.
</Analogy>

## Why it matters

"How would you scale this?" is in every system design interview. A good answer separates stateless tiers (scale out freely) from stateful ones (databases, caches — harder), and recognises shared bottlenecks.

## Vertical versus horizontal

| | Vertical (scale up) | Horizontal (scale out) |
|---|---|---|
| How | more CPU/RAM/disk on one machine | more machines behind a load balancer |
| Pros | simple; no code changes; no distribution problems | near-unlimited ceiling; redundancy; incremental |
| Cons | hard ceiling; expensive at the top end; single point of failure | needs statelessness or partitioning; distributed-systems complexity |
| Typical for | databases (first), caches | web/API tiers, workers |

Vertical scaling is underrated: modern machines have hundreds of cores and terabytes of RAM. Start there for stateful components and scale out when you must.

## Statelessness

A **stateless** service keeps no per-client data in memory between requests. Everything needed comes with the request (a token) or from shared storage (database, cache).

Making a service stateless:

- Sessions in Redis or signed tokens (JWT) instead of server memory.
- Uploaded files to object storage, not local disk.
- Scheduled jobs coordinated with a lock or a dedicated scheduler, not "whichever server runs cron".
- In-memory caches are fine as optimisations, as long as correctness doesn't depend on them.

**Sticky sessions** (the load balancer pins a user to a server) are a workaround, not a solution: uneven load, and sessions lost when the server goes.

## Where scaling gets hard

Stateless tiers scale almost linearly. The limits are the **shared, stateful** parts: the database primary, a global counter, a lock, a single queue partition. Scaling those requires **partitioning** (each node owns part of the data), **replication** (for reads), or **caching** — and redesigning hotspots such as global counters.

## Amdahl's Law

If a fraction **s** of the work is serial (can't be parallelised), the maximum speed-up with N processors is:

> speed-up = 1 ÷ (s + (1 − s) ÷ N)

With just 5% serial work, the speed-up can **never** exceed 20×, however many machines you add.

## The Universal Scalability Law

Real systems are worse than Amdahl: nodes also spend time **coordinating** with each other (cache coherence, locks, consensus, cross-node chatter). Neil Gunther's USL adds a **coherency** term that grows with the number of nodes — so throughput rises, flattens, and then **falls**.

Lessons:

- Minimise **serial** sections: global locks, single-threaded coordinators, one hot row.
- Minimise **coordination**: avoid designs where every node talks to every other, or every request needs a distributed lock.
- **Partition** so nodes work independently ("shared-nothing").
- **Measure** scaling under load; past a point, more nodes can reduce throughput.

## Autoscaling

Scale stateless tiers automatically on a metric that reflects load: CPU (target ~60–70%), requests per instance, queue depth for workers, or event-loop delay for Node services. Account for warm-up time (new instances take time to start and fill caches), and scale **down** conservatively to avoid flapping. Ensure dependent stateful systems (database connections!) can absorb the extra instances.

<Callout type="pitfall" title="Common mistakes">

- Storing sessions or uploads on local servers, then adding a load balancer.
- Scaling the web tier while the database is the bottleneck.
- Global counters or locks on every request.
- Assuming doubling servers doubles throughput.
- Autoscaling app servers without checking the database's connection limit.

</Callout>

## Explaining it in an interview

<InterviewAnswer question="How would you scale a web application?">

I'd make the application tier stateless — sessions in Redis or signed tokens, files in object storage — so I can run many identical instances behind a load balancer and autoscale on CPU or request rate, aiming for around 60–70% utilisation. The data tier is the hard part: I'd scale it vertically first, add read replicas and caching for read-heavy load, and partition by a good key when writes or storage outgrow one machine. Throughout, I'd watch for serial bottlenecks — global locks, single hot rows, a single queue partition — because Amdahl's Law caps speed-up by the serial fraction, and coordination between nodes can even make throughput fall as you add nodes, as the Universal Scalability Law shows.

<Fragment slot="deeper">

- **Why are stateless services easy to scale?** Any instance can serve any request, so instances are interchangeable.
- **Sticky sessions — good or bad?** A workaround; uneven load and lost sessions on failure.
- **What limits horizontal scaling?** Shared state, serial sections and coordination overhead.

</Fragment>
</InterviewAnswer>
