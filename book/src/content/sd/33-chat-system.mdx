A chat system — think WhatsApp, Slack or Messenger — lets users send messages to individuals and groups, delivered in real time when the recipient is online and stored for later when they're not. The interesting parts are **persistent connections** (millions of open WebSockets), **routing** a message to whichever server holds the recipient's connection, **ordering** and **storing** messages per conversation, and **presence** ("online", "typing…").

<Analogy>
  A switchboard operator in a huge hotel. Each guest has a direct line to one of many operators (their connection). When a guest sends a message to another, the operator looks up which colleague is connected to the recipient and passes it along — and if the recipient is out, the message goes into their pigeonhole (storage) and a note is slipped under their door (push notification).
</Analogy>

## 1. Requirements

**Functional**

- One-to-one and group chats (groups up to, say, 500 members).
- Real-time delivery when online; stored and delivered later when offline (with push notifications).
- Message history, synced across a user's devices.
- Delivery status (sent, delivered, read), typing indicators, online presence.
- Out of scope: voice/video, end-to-end encryption details (mention).

**Non-functional**

- Low latency (under ~200 ms end to end in-region).
- Messages must **never be lost** and must appear **in order** within a conversation.
- Highly available; scale to e.g. 50 million daily users.

## 2. Estimates

- 50M DAU × 40 messages/day = 2 × 10⁹ messages/day ≈ **23,000/s** average, ~100k/s peak.
- Concurrent connections: maybe 20% online at peak → **10 million WebSockets**. At ~50k–100k connections per gateway server → **100–200 gateway servers**.
- Storage: 2 × 10⁹ × 200 bytes ≈ **400 GB/day** → ~150 TB/year → a horizontally scalable store, partitioned by conversation.

## 3. Connections and protocol

Clients keep a **persistent WebSocket** connection to a **gateway** (chat server). HTTP polling would waste resources and add latency; WebSockets give full-duplex, low-latency messaging. Mobile apps fall back to **push notifications** (APNs/FCM) when backgrounded.

## 5. Deep dive: sending a message reliably

- **Persist first, then deliver**: an acknowledged message is never lost even if delivery fails.
- **Client message IDs** make retries idempotent.
- **Ordering**: assign a per-conversation **sequence number** (from the conversation's partition leader, or a per-conversation counter). Clients sort by it and detect gaps (`I have up to 1040, server says 1042 → fetch 1041`).
- **Sync**: each device tracks the last sequence it has per conversation; on reconnect it asks "give me everything after N".

## 6. Deep dive: storage

Access pattern: "latest N messages of conversation C", "messages after sequence S". Partition by **conversation ID**, cluster by sequence number:

```text
messages: partition key = conversation_id, sort key = seq
          (sender_id, created_at, body, type, client_msg_id)
```

A wide-column store (Cassandra/ScyllaDB — Discord's choice) or DynamoDB fits this perfectly: writes spread across conversations, and reading a conversation is one contiguous range. Large group conversations are hot partitions; bucket them by time (`conversation_id + month`).

Separately, a **user inbox** table holds each user's conversations with last-message preview and unread counts, for the conversation list screen.

## 7. Deep dive: group chats

For a 500-member group, a message must reach up to 500 devices.

- Store the message **once** in the conversation.
- **Fan out delivery**: look up members, then their gateways (batch registry lookups), and push. Offline members get notifications (batched / collapsed).
- Very large channels (100k+ members, Slack/Discord style) switch to **pull on open**: don't push every message to everyone; clients fetch when they view the channel.

## 8. Presence and typing

Presence is high-volume and can tolerate staleness:

- Gateways update a user's **last-seen heartbeat** in Redis (with a TTL of ~60 s); no heartbeat → offline.
- Publish presence changes only to users who are currently viewing that person (subscribed), not to all their contacts.
- Typing indicators are **ephemeral**: routed through pub/sub, never stored, dropped if late.

## 9. Scaling and failure

- Gateways scale horizontally; on gateway failure, clients reconnect (with jittered backoff) to another and resync from their last sequence number.
- The session registry is ephemeral and rebuilt as clients reconnect.
- Multi-region: users connect to the nearest region; conversations have a home region for ordering; cross-region messages are forwarded.
- Security: TLS everywhere; end-to-end encryption (Signal protocol) means servers store only ciphertext — features like server-side search then move to the device.

<Callout type="pitfall" title="Common mistakes">

- Using HTTP polling instead of persistent connections.
- Delivering before persisting (lost messages on failure).
- Relying on timestamps for message order.
- Broadcasting presence to every contact on every change.
- Writing a group message once per member into storage.

</Callout>

## Explaining it in an interview

<InterviewAnswer question="Design a chat application like WhatsApp.">

Clients hold persistent WebSocket connections to a horizontally scaled gateway tier, and a Redis session registry maps each user to the gateway holding their connection. When a user sends a message with a client-generated ID, the message service assigns the next sequence number in that conversation, persists it — deduplicating by client ID — and only then acknowledges, so acknowledged messages are never lost. It then routes the message to the recipients' gateways via pub/sub, or sends a push notification if they're offline. Messages are stored in a wide-column store partitioned by conversation ID and sorted by sequence, so loading history is one range read; devices sync by asking for everything after their last sequence number, which also fills gaps. Groups store the message once and fan out delivery; presence uses heartbeats with TTLs and is published only to interested viewers; typing indicators are ephemeral.

<Fragment slot="deeper">

- **How do you order messages?** Per-conversation sequence numbers from a single owner, not timestamps.
- **What happens when a gateway dies?** Clients reconnect elsewhere and resync from their last sequence number.
- **Why partition by conversation?** History reads are contiguous and writes spread across partitions.

</Fragment>
</InterviewAnswer>
