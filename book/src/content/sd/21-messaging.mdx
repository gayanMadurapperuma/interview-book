Asynchronous messaging lets services communicate without waiting on each other. A producer hands a message to a **broker**; consumers process it when they can. That decouples availability (the consumer can be down for a while), absorbs traffic spikes, and lets one event trigger many reactions. There are three main models: **work queues** (each message processed by one worker), **publish/subscribe** (each message delivered to every interested subscriber) and **logs** (an ordered, replayable record that many consumers read at their own pace).

<Analogy>
  A **queue** is a ticket rail in a kitchen: each order ticket is taken by exactly one cook. **Pub/sub** is a radio broadcast: everyone tuned in hears every announcement, and if you weren't listening, you missed it. A **log** is a newspaper archive: every edition is kept in order, and each reader keeps a bookmark — new readers can start from last week, or from the very first issue.
</Analogy>

## Why it matters

Almost every system design uses a queue or a log somewhere — for background jobs, fan-out, event-driven integration, or smoothing load. Interviewers ask which model to use, the difference between SQS and Kafka, ordering guarantees, and how to handle failures and duplicates.

| | Work queue | Pub/sub | Log |
|---|---|---|---|
| Each message goes to | one consumer | every subscriber | every consumer group (one member per partition) |
| After processing | deleted | gone (unless subscriber queues persist) | **kept** until retention expires |
| Replay | no | no | yes — rewind the offset |
| Ordering | best-effort (FIFO variants exist) | none | **per partition** |
| Scaling consumers | add workers | add subscribers | add partitions + consumers |
| Examples | SQS, RabbitMQ, BullMQ | SNS, Google Pub/Sub, Redis pub/sub | Kafka, Kinesis, Redpanda, Pulsar |
| Good for | background jobs, task distribution | fan-out notifications | event streaming, CDC, analytics, rebuilding state |

A very common AWS pattern combines them: **SNS topic → one SQS queue per subscribing service** — pub/sub fan-out, with each service getting a durable queue of its own.

## Work queues in detail

Essentials:

- **Acknowledge after processing**, so failures lead to redelivery (and make handlers idempotent).
- **Dead-letter queue (DLQ)**: after N failed attempts, move the message aside for inspection instead of retrying forever ("poison message").
- **Visibility timeout** longer than the processing time (extend it for long jobs).
- Scale workers on **queue depth** or age of the oldest message.

## Logs in detail (Kafka)

A Kafka **topic** is split into **partitions**. Each partition is an append-only, ordered log; each message gets an increasing **offset**. Messages with the same **key** go to the same partition, so they're ordered relative to each other.

Key points:

- **Ordering is per partition**, not per topic. Choose keys so related events share a partition.
- **Parallelism** is capped by the partition count; plan it ahead (increasing partitions changes key → partition mapping).
- **Consumer lag** (latest offset − committed offset) is the key health metric.
- **Retention** (days, or forever with compaction) allows replaying history, rebuilding read models, and adding new consumers that start from the past. **Log compaction** keeps only the latest message per key — a changelog of current state.

## Message design

- Include a unique **message ID** (for dedup), an **event type**, a **schema version**, a timestamp and the entity **key**.
- Prefer **business events** ("PaymentCaptured") over commands disguised as events.
- Keep payloads reasonably small; put large blobs in object storage and send a reference.
- Use a schema registry (Avro, Protobuf, JSON Schema) for evolution.

<Callout type="pitfall" title="Common mistakes">

- Non-idempotent consumers on at-least-once brokers.
- No dead-letter queue — one bad message blocks a partition or retries forever.
- Expecting global ordering across a Kafka topic.
- Too few partitions to scale consumers later.
- Using pub/sub without persistence for events that must not be lost.
- Publishing events without an outbox.

</Callout>

## Explaining it in an interview

<InterviewAnswer question="What's the difference between a queue like SQS and a log like Kafka?">

A work queue distributes messages so each is processed by one consumer and then deleted — ideal for background jobs — with visibility timeouts for redelivery and dead-letter queues for poison messages. A log like Kafka keeps messages in ordered, partitioned, append-only logs for a retention period; consumers track their own offsets, so several consumer groups read the same events independently and can replay history. Ordering is guaranteed within a partition, so I key messages by entity ID, and parallelism is bounded by the number of partitions. Pub/sub, like SNS, broadcasts each message to all current subscribers, and is often combined with a queue per subscriber for durability. All of these are typically at-least-once, so consumers must be idempotent.

<Fragment slot="deeper">

- **How do you keep events for one order in order in Kafka?** Use the order ID as the key so they share a partition.
- **What is consumer lag?** How far a consumer group is behind the latest offset.
- **What is a DLQ for?** Isolating messages that repeatedly fail so they don't block or loop.

</Fragment>
</InterviewAnswer>
